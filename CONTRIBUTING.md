# Contributing

tree-sitter-varyk is the Tree-sitter grammar for Varyk. Varyk is
experimental and pre-1.0: anything may change, and a new feature or a
breaking change bumps the minor version. Contributions are welcome;
small, focused pull requests are the easiest to review. The project has
one maintainer, so reviews are best effort and a pull request may wait a
while; a reminder after two weeks is welcome.

The language is defined by the compiler,
[`Varyk-Lang/varyk`](https://github.com/Varyk-Lang/varyk), whose
[`docs/language.md`](https://github.com/Varyk-Lang/varyk/blob/main/docs/language.md)
is the reference; the grammar's design is in `docs/specs/` here.

## Build and test

You need Node.js for the tree-sitter CLI and a C compiler, since
`tree-sitter test` and `tree-sitter parse` compile the parser. Install
the pinned CLI, 0.27.1, as CI does:

```sh
npm install -g tree-sitter-cli@0.27.1
tree-sitter --version    # tree-sitter 0.27.1
```

Before opening a pull request, run the same checks CI runs:

```sh
tree-sitter generate --abi 14
git status --porcelain -- src    # must print nothing
tree-sitter test
```

`tree-sitter test` runs the corpus tests and the highlight tests
together. Then check the grammar against the compiler's own programs
with a checkout of the compiler:

```sh
git clone --depth 1 https://github.com/Varyk-Lang/varyk /tmp/varyk
scripts/drift.sh /tmp/varyk
```

It parses every `.vr` file under the compiler's `examples/` and
`crates/varyk/tests/fixtures/`, skipping the fixtures that are syntax
errors on purpose, and lists each file that does not parse cleanly with
the position of its first `ERROR` or `MISSING` node. The "Drift"
workflow runs it every night, on demand, and on every pull request. It
is not a required check: a red run means the compiler moved on and the
grammar is behind, not that the pull request is wrong. Fix it with a
corpus case for the missed form and a grammar change, never by
extending the skip list.

## Where things are

- `grammar.js` is the grammar. It mirrors the compiler's parser
  (`crates/varyk-syntax/src/parser/`), with node names after
  `tree-sitter-rust`.
- `queries/highlights.scm` is the highlight query.
- `test/corpus/` holds the corpus tests, one file per area (`items.txt`,
  `statements.txt`, `expressions.txt`, `patterns.txt`, `types.txt`,
  `comments.txt`); `test/highlight/` holds the highlight test.
- `src/` is generated by `tree-sitter generate --abi 14` and committed;
  never edit it by hand.
- `scripts/drift.sh` is the drift run, with its skip list at the top.
- `docs/specs/` holds the design and `docs/plans/` the plans it was
  built from.

## Commit messages and releases

Releases are cut by
[release-please](https://github.com/googleapis/release-please) from the
commit history on `main`, so every commit that lands on `main` carries a
conventional prefix. A pull request with one concern is squash-merged
with a conventional title; a pull request with several concerns is
rebase-merged with one conventional commit per concern.

| Prefix | Use it for | Effect on the release |
|---|---|---|
| `feat:` | a new capability | bumps the version, listed in the changelog |
| `fix:` | a bug fix | bumps the version, listed in the changelog |
| `docs:` | documentation only | no bump, not listed |
| `test:` | tests only | no bump, not listed |
| `ci:` | workflows and release automation | no bump, not listed |
| `chore:` | maintenance, scaffolding | no bump, not listed |
| `refactor:` | code change with no behavior change | no bump, not listed |

A `!` after the prefix (`feat!:`) marks a breaking change. Before 1.0,
`feat` and a breaking change bump the minor version and `fix` bumps the
patch version.

Keep `<` and `>` out of commit subjects and `BREAKING CHANGE:` footers:
write `Option of T`, not `Option<T>`. release-please copies them into
the release pull request and reads that body as HTML, where an unclosed
`<T>` hides what follows it and leaves the release untagged. The
`Commit messages` check enforces this on every pull request.

release-please opens a release pull request on `main` with the version
bump in `tree-sitter.json` and `CHANGELOG.md`. Merging that pull
request is the release decision: it creates the tag `vX.Y.Z` and the
GitHub release. Nothing is published to a package registry; a release
is a tag and a changelog, and the Zed extension pins a release's
commit.

## Reporting bugs

Open an issue with the smallest `.vr` file that shows the problem and
the output of `tree-sitter parse` on it. For security problems, see the
security policy shared by every Varyk-Lang repository:
<https://github.com/Varyk-Lang/tree-sitter-varyk/security/policy>.
